# 00_prep — сборка данных

Первый слой проекта. Превращает сырые выгрузки Spotify (JSON + CSV) в 15 паркетов `data/00_output/`. Всё, что идёт дальше — EDA, методология, дашборд — читает **только эти паркеты**, к сырым файлам больше не обращается.

Четыре ноутбука, каждый создаёт свою часть:

| Ноутбук | Что собирает |
|---|---|
| `00_0_orphans_detect` | Находит сирот, готовит CSV для загрузки в Spotify |
| `00_1_build_full_history` | История + аудио-фичи → 8 паркетов |
| `00_2_account_data` | Account data: библиотека, плейлисты, владельцы → 7 паркетов |
| `00_3_quality_check` | Проверяет целостность всех 15 паркетов |

Единственный ручной шаг — загрузка сирот в Spotify и экспорт через Exportify. `00_0` делает его максимально безболезненным (см. ниже).

**Код.** Ноутбуки используют `src/paths.py` (`get_data_path()`, `get_project_root()`). `src/` уже в репозитории — ничего настраивать не нужно, но ноутбуки должны лежать внутри клонированного проекта.

Если папок `data/` ещё нет — ячейка 0 ноутбука `00_0` создаст всю структуру сама (`Spotify/`, `Exportify/`, `00_output/` и подпапки). Можно запустить её первой, разложить файлы по готовому дереву, потом запускать остальные ячейки.

## Как получить выгрузку Spotify

Две отдельные выгрузки, запрашиваются на странице [Account Privacy](https://www.spotify.com/account/privacy/):

| Что запросить | Что придёт | Куда положить |
|---|---|---|
| **Account data** | JSON: `Playlist*.json`, `YourLibrary.json`, `UserAttributes.json`, `Inferences.json`, `SearchQueries.json`, `Follow.json` и др. | `data/Spotify/Spotify_Account_ Data/` |
| **Extended streaming history** | JSON `Streaming_History_Audio_*.json` — по одному на год | `data/Spotify/Spotify_ Extended_Streaming_History/` |

Выгрузки приходят на почту **по очереди, в разных письмах**, в течение нескольких дней (иногда до 30). В архиве — папка `Spotify Account Data/` или `Spotify Extended Streaming History/`, внутри — файлы.

## Как получить CSV из Exportify

Spotify API не отдаёт аудио-фичи (`valence`, `energy`, `danceability` и остальные) — только Exportify.

1. Открыть https://exportify.net/ и авторизоваться через Spotify.
2. Дождаться, пока Exportify подтянет список плейлистов.
3. Нажать **Export** у каждого плейлиста — включая `Liked Songs`.
4. Скачанные CSV положить в `data/Exportify/spotify_playlists (<account>)/`.

`<account>` — произвольное имя (ник, `main`). Ноутбуки читают по маске `spotify_playlists (*)/*.csv`. Один аккаунт — можно в одну папку.

**Куда не класть:** `data/Exportify/exportify_orphan_export/` — отдельная папка, её заполняет `00_0` (см. «Про сирот»).

```
00_0  →  найти сирот
        ↓
      [ручной шаг: загрузить сирот в Spotify,
       экспортировать через Exportify,

```

**Порядок обязателен.** `00_2` (ячейка 8) читает `playlist_links.parquet`, созданный в `00_1` (ячейка 3.1). Запускать `00_2` до `00_1` нельзя — упадёт на `FileNotFoundError`.

**Нет сирот?** Если все треки уже в плейлистах или лайках — `00_0`
пропускается, начинай с `00_1`.

## Про сирот — зачем это вообще

Exportify отдаёт аудио-фичи (`valence`, `energy`, `danceability` и
остальные) только для треков, которые лежат в плейлистах или лайках.
Треки, которые слушались, но ни в плейлист, ни в лайки не попали —
**сироты** — остаются без фич. Это не редкий случай: **без фич
оказывается большая часть истории**, и без них не собрать ни звуковой
портрет, ни Sound-кластеры, ни точки разладки на звуке, ни большинство
индексов дашборда.

Exportify не умеет «дать фичи по списку URI» — только экспортировать
плейлисты. Значит сирот надо **сначала положить в плейлист**, чтобы
Exportify их увидел. Это единственный ручной шаг во всём пайплайне.
`00_0` делает его максимально безболезненным: сам находит сирот, сам
создаёт плейлисты (если API), сам проверяет результат.

**Логика в три шага:**

1. Читает все JSON с историей прослушиваний, собирает уникальные
   `spotify_track_uri`.
2. Читает все CSV из Exportify (плейлисты + лайки), собирает уникальные
   URI. Дедупликация общая, не по аккаунтам.
3. Вычитает: `сироты = история − (плейлисты ∪ лайки)`.

Сирота определяется по пересечению всех аккаунтов: трек, который слушался хотя бы в одном аккаунте, но не сохранён ни в один плейлист и ни в одни лайки ни одного из аккаунтов — сирота. Разбивка по аккаунтам на этом шаге потеряла бы смысл, поэтому 00_0 пишет один общий CSV.

**Что сохраняется:**
- `orphans_uris.csv` — все сироты, одна колонка `spotify_track_uri`;
- `orphans_batch_NN.csv` — батчи по 10 000 URI;
- `created_playlists.json` — метаданные плейлистов (при `METHOD='api'`).

Ограничение CSV — нет. Ограничение **плейлиста в Spotify** — 10 000
треков. Отсюда `BATCH_SIZE = 10_000`: один батч = один приватный плейлист
`__ORPHANS_NN`.

**Развилка `METHOD` (ячейка 5):**

**API (автоматически).** `METHOD = 'api'` (ячейка 6a). Нужен
`spotify_credentials.json` рядом с ноутом (в `.gitignore`), Premium-аккаунт
и один раз пройти OAuth. Ноутбук сам создаёт приватные плейлисты
`__ORPHANS_01`, `__ORPHANS_02`, … и добавляет туда треки батчами по 100
(лимит API Spotify). Защита от дублей: если плейлист `__ORPHANS_NN` уже
есть и число треков совпадает — пропускает; если число другое — не
трогает и помечает конфликтом.

`spotify_credentials.json` создаётся один раз: в
[Spotify Developer Dashboard](https://developer.spotify.com/dashboard)
создаёте приложение, копируете `client_id` и `client_secret`, добавляете
`redirect_uri` (например, `http://127.0.0.1:8080/callback` — тот же, что
указан в приложении). Файл:

```json
{
  "client_id": "...",
  "client_secret": "...",
  "redirect_uri": "http://127.0.0.1:8080/callback"
}
```

`redirect_uri` должен совпадать с зарегистрированным в Dashboard —
иначе OAuth упадёт. Файл в `.gitignore`, ключи не попадают в репозиторий.

**Вручную.** `METHOD = 'manual'` (ячейка 6b). Ноутбук печатает
пошаговую инструкцию:
1. создать приватные плейлисты `__ORPHANS_NN` в **десктопном** Spotify
   (веб-версия массовую вставку не поддерживает);
2. скопировать колонку `spotify_track_uri` из CSV → вставить в плейлист
   через Ctrl+V — десктоп принимает весь батч за одну вставку;
3. экспортировать каждый плейлист через Exportify;
4. положить CSV в `data/Exportify/exportify_orphan_export/`;
5. запустить `00_1_build_full_history.ipynb`.

После этого `00_1` подхватывает CSV из `exportify_orphan_export/`.

**Финальная ячейка (7)** показывает три числа:
- сколько сирот найдено;
- сколько уже выгружено (процент покрытия);
- сколько выгруженных треков имеют аудио-фичи (проверка, что Exportify
  не вернул пустые колонки).

## Проверки `00_3`

Девять блоков, от загрузки до сводки:

1. **Загрузка** — все паркеты на месте.
2. **Time consistency** — `ts − ts_utc = 0`, диапазон дат совпадает
   с ожидаемым.
3. **Clean data** — пустые URI, NaN в жанрах, `played_frac` (NaN, inf),
   `duration_ms == 0`.
4. **Keys & links** — дубли по правилам, целостность URI между файлами.
5. **Ranges** — аудио-фичи в [0, 1], `popularity` в [0, 100],
   `tempo` в [10, 300].
6. **Flags consistency** — короткие прослушивания помечены как skip,
   в `eda_ready` нет аналитических колонок, `first_listen` только у сирот.
7. **Forbidden columns** — нет подкастов и аудиокниг.
8. **UNTRANSLATED** — нет `UNTRANSLATED:` в жанрах.
9. **Summary** — отчёт ✅ / ⚠️ / ❌.

## Маппинг жанров

`references/genre_mapping.json` — фиксированный словарь под текущий профиль. Формат: `{"ru_genre": "en_genre"}`. На других данных часть жанров может не покрыться: жанры вне маппинга остаются как есть, кириллица уходит в `unknown`. Если покрытие низкое (доля `unknown` видна в ячейке 5.1 ноутбука `00_1`) — собрать свой `genre_mapping.json` из своих данных и заменить файл.
